## 1. 设计目标与约束

### 1.0 评审决策（本文档的输入约束，已定案）

| # | 决策 | 架构影响 |
|---|------|---------|
| D1 | 本项目是**管理平台**，不关注计费服务流量 | 删除 calc-service/snapshot-service；高并发缓存体系、single-flight 回源等设计移出范围 |
| D2 | 事务**不关注快照延迟，关注数据是否一致** | 一致性设计聚焦"配置数据"：组粒度原子发布、时间区间不重叠不变式、content_hash 可验证；v2.1 并按决策删除下游上报核查与 Bundle 机制 |
| D3 | **不涉及交易链路** | 对交易系统的 RPC 契约、下单降级预案移出范围；下游仅作为"配置消费者"对待 |
| D4 | **不涉及计价链路** | 计价引擎（责任链执行、兜底价、P99 预算）归下游计费系统；本平台只定义**计算模板**并保证发布正确 |
| D5 | （v2.2 确认）费用:方案 = **1:N 实例并存**，不同实例绑定不同维度（城市/区域/国家…）；方案绑维度才在该维度生效 | I1 重定域到实例级；新增 **I4 维度互斥不变式**（同费用并存实例命中集两两不相交）；发布锁升级费用级；计费侧按(费用+维度点)唯一命中 |
| D6 | （v2.3 确认）互斥冲突**不设"允许重叠按规则决胜"的柔性模式**；"默认+专属"是常态运营需求 | 冲突即拒绝发布+冲突报告；默认方案用 NOT_IN 补集表达；I1/I4 校验改为闭旧+转正后的**事务内终态复核**，使"改默认缩集+新增专属"可在同一次组发布内原子完成（data-model §6.2/§7） |
| D7 | （v2.4 确认）容量假设与剩余口径**不再单独讨论，按默认设计关闭**：维度随方案版本发布 / 单时区 DATETIME(3) / canonical 不对外 / 无组级生效时间 / 量级假设成立 | 各文档评审点全部关闭；量级发生数量级变化时重开 ADR-16 |
| D8 | （v2.5）**不引入缓存层**：所有读接口（分发 + 管理端）直查 DB | 删除 C1/C2/C3 缓存、预热、bypass/fail-open 全套机制；读压 <100 QPS 索引可覆盖；"正确性不依赖中间件"升级为 **Redis 不在读链路** |
| D9 | （v2.5）Redis 用途收窄：**仅承担方案编辑/修改/删除的排他锁** | 原发布锁（组+费用级）删除，发布并发由 DB `FOR UPDATE`+CAS+终态复核独扛；原任务锁删除，job 防重靠 XXL-JOB 单派发+幂等；Redis 故障仅编辑入口 fail-close，发布/分发不受影响（cache-and-lock v3.0） |
| D10 | （v2.5）新增三个功能模块：**方案批量导入导出 / 方案-维度绑定管理 / 沙盒试算** | 导入复用既有校验矩阵产出 DRAFT；维度绑定升级为独立管理视图含冲突预检；试算为配置验证专用内网能力，**不进入分发契约、不承接在线计费流量，D4 边界不变**（详 §4.4） |

### 1.1 架构目标

| # | 目标 | 度量 |
|---|------|------|
| G1 | **配得清**：业务→场景→费用组→费用→方案→维度/因子/模板 模型层次清晰可管理 | 新业务场景接入零代码（纯配置） |
| G2 | **管得住**：任何配置变更有审批、有版本、有审计、可回滚 | 100% 写操作可回溯到人 |
| G3 | **发得准**：发布数据强一致——版本内多维度/因子/双模板**原子生效**，无中间态 | 发布事务覆盖 100%；下游读不到半成品配置 |
| G4 | **查得对**：展示与计算模板发布时成对强校验；任意历史时点配置可回放 | 绑定校验拦截率 100%；时点查询可复现 |
| G5 | **够用可扩展**：架构与数据量级匹配管理平台定位，不过度设计，预留增长路径 | 见 §6 容量测算 |

### 1.2 约束

- 技术栈：Spring Boot / MyBatis / Redis / Dubbo / MySQL；Nacos 注册配置；RocketMQ 仅用于发布事件通知（可选通道，下游可纯拉取）。
- **事务约束（不变）**：仅 Spring 本地事务，不引入分布式事务框架。
- 一致性口径：**平台内部强一致（单库事务 + 组粒度原子发布 + 区间不重叠不变式）**；下游按时间版本拉取，其自身应用动作的及时性/一致性由下游负责（决策 D1/D2 收敛后口径）。

## 2. 总体架构

### 2.1 架构图

```
┌─────────────────────────────────────────────────────────────────┐
│ 【使用者】 定价运营 / 商务 / 审批 / 审计                            │
└──────────────┬──────────────────────────────────────────────────┘
               │ Web(REST)
┌──────────────▼──────────────────────────────────────────────────┐
│         ★ Pricing Management 管理平台（模块化单体, 单一部署）        │
│                                                                  │
│  pm-admin        pm-application(用例/事务)      pm-delivery      │
│  管理端BFF  ──▶  组配置/发布编排/审批     ──▶  分发服务          │
│  鉴权/审计切面    模板中心/因子中心/场景管理     Dubbo+HTTP OpenAPI │
│                                                                  │
│  pm-domain(业务/场景/方案/因子/模板/版本 聚合与校验)                │
│  pm-infrastructure(MyBatis/Redis锁/MQ/审计)                      │
│  pm-job: 分区维护 · 历史归档 · 审计清理（无定时生效 job，时间自身即版本开关）        │
└──────┬───────────────────────┬───────────────────────────────────┘
       │ 发布事件(MQ, best-effort) │ 拉取生效集/方案内容(Dubbo/HTTP, 主通道)
┌──────▼───────────────────────▼───────────────────────────────────┐
│ 【下游配置消费者】(独立系统, 边界外)                                 │
│  • 计费引擎系统: 拉计算模板+因子值 → 自行执行计价(流量/性能与我无关)   │
│  • 费用展示服务: 拉展示模板 → 渲染"费用怎么算"                       │
│  • 二者均: 按时间版本自行拉取与感知变更(平台不再核查下游状态)        │
└──────────────────────────────────────────────────────────────────┘
```

### 2.2 架构风格决策

| 决策 | 选择 | 理由 |
|------|------|------|
| 服务模式 | **模块化单体**（Maven 多模块 + 单一部署单元，admin 与 delivery 可按需独立拆部署） | 管理平台 QPS 极低（内部用户+下游低频拉取），微服务拆分只增加分布式复杂度；模块边界=未来服务边界，保留拆分能力 |
| 内部结构 | DDD 分层（admin/delivery → application → domain → infrastructure） | 配置模型校验规则复杂（双模板绑定、因子完备性），领域层集中收敛规则 |
| 对外分发 | **拉取为主（当前生效集 + 按费用/时点取内容），MQ 通知为辅（best-effort）** | 拉取模式下游自主、可重试、天然幂等；MQ 只做加速，丢了不影响正确性 |
| 一致性 | 内部单库本地事务；对外**时间区间版本化（不重叠不变式）+ content_hash** | 对齐决策 D2：不追求"下游实时一致"，追求"发布原子、历史可回放、内容可验证" |
| 数据分片 | 不分库分表（测算见 §6），审计日志 MySQL 月分区 | 对齐决策 D1：管理平台量级由"费用数×改价频次"决定，非订单量级 |

## 3. 核心域模型（功能骨架，详见 pricing-model.md / data-model.md）

```
业务 biz_line 1─N 场景 pricing_scene 1─N 费用组 pricing_fee_group 1─N 费用 pricing_fee_item
                                                              │ (名称/编码/顺序/必填)
                                                    1─N 方案 pricing_scheme(版本行)
                                        ┌──────────────────┼──────────────────┐
                                        ▼                  ▼                  ▼
                                绑定维度 scheme_dimension  因子赋值 factor_value  模板引用 scheme_template
                                (★同为 start/end 时间版本)  (四形态)             CALC + DISPLAY 成对锁定
不变式 I1: 同一方案实例(root_scheme_id，仅内部使用)区间不重叠 → 实例任一时刻至多一个生效版本
不变式 I4: 同一费用并存生效实例的命中维度集合两两互斥 → (费用×维度点×时点) 唯一命中, 无需优先级决胜
平台级字典: 因子字典 pricing_factor(值类型/校验规则/分类)
            模板库 pricing_template(CALC|DISPLAY, 内容不可变追加)
```

关键规则（平台一致性的模型根基）：

1. **场景约束因子集**：方案只能使用其场景 `factor_scope` 内的因子 → 从源头保证下游计费引擎拿到的输入完备。
2. **双模板成对**：每个已发布版本必须且只能含 1 个计算模板 + 1 个展示模板，且展示的变量槽必须绑定计算模板的输出字段（§pricing-model.md 校验矩阵）。
3. **时间区间版本化**（v2.1，取代 Bundle 冻结）：发布=同事务内闭旧版 end + 新版转正 start；区间一经发布不可变；定时预发布行由时间自身切换，**不依赖 job 正确触发**；任意时点配置可由区间+子表行装配重建（审计/回滚数据基础）。
4. **组粒度一并配置**：一个费用组的全部费用在同一页面配置、一张审批单、一个发布事务整批生效——组内永不出现新旧混版。

## 4. 核心流程

### 4.1 费用组配置与发布（主动脉，事务与一致性焦点）

```
组配置页: 一并配置组内全部费用(可多实例, 各绑维度; 每实例草稿版本行: 维度/因子赋值/模板引用, 编辑锁+乐观锁)
 → 提交前校验(必填费用配齐 + 领域规则集: 因子完备/双模板配对/变量绑定/取值合法/区间不重叠(I1)/维度互斥(I4))
 → 整组提交审批(一张审批单覆盖组内全部方案)
 → 审批通过 → 发布【单个本地事务】(步骤详见 data-model §7):
     ① 事务内逐个(按 fee_id 升序)锁该费全部开区间生效行 SELECT...FOR UPDATE(含兄弟实例; v2.5 起无 Redis 发布锁, D9)
     ② 重算各方案 content_hash(canonical 序列化)
     ③ UPDATE 旧版本行 end_time = 新版本 start_time(闭旧)
     ④ UPDATE 草稿行 status=PUBLISHED + start/end + content_hash(转正, 子表行不动)
     ⑤ 终态复核 I1/I4(事务视图=发布后终态, 违规即回滚; D6: 支撑默认缩集+新增专属同组原子变更)
     ⑥ approval_flow 终态 + audit_log 逐行留痕
     提交后: best-effort 投 MQ 发布事件(失败仅告警, 不影响正确性)
 → 生效方式: 立即 / 定时(start=未来时间, 时间自身切换, 零 job 依赖) / 灰度标记(下游自主)
```

失败路径：事务任一步失败整体回滚，组内全部费用停留在旧版本——**无半发布、无组内混版**。

### 4.2 下游分发与消费（对齐 D1：平台不管流量，只管给对）

```
下游循环: 轮询当前生效集(费用粒度: schemeId + start_time + content_hash, 直查 DB·无缓存 D8)
         → 发现变化 → 按 费用+时点 拉方案全量内容(维度/因子/双模板/槽绑定)
         → 本地复算/比对 content_hash → 应用
平台视角: 生效性由时间区间定义, 接口只读幂等; 下游多久应用新版本是下游的事
```

### 4.3 历史回放与审计（v2.1 取代一致性核查）

```
任意时点 t 的生效配置 = WHERE status='PUBLISHED' AND start<=t AND (end>t OR end IS NULL) + 子表装配
→ 客诉/审计: 按订单时点还原当时价格配置; 按内部 root_scheme_id 看完整版本时间线
→ 回滚 = 复制历史版本内容为新行发布(rollback_from_id 溯源), 区间链保持线性不倒退
→ 正确性防线从"事后核查下游"前移到"发布事务内校验 + 不可变历史可验证"(决策 D2 口径)
```

### 4.4 功能补充（v2.5 新增，决策 D10）

**① 方案批量导入导出**

- 导入：下载模板（CSV/JSON）→ 运营批量填写方案/维度绑定/因子赋值 → 导入接口逐行校验（**复用提交前同一套规则集**：必填/因子完备/双模板配对/B1~B5/I1 预检）→ 全部合法才生成 **DRAFT** 行（绝不直发），失败行逐行错误报告；整文件单事务，要么全导要么全回滚；事务内分批写（≤500 行/批，同事务 savepoint 不做——回滚即全废）；
- 实现形态：导入采用**模板方法**——`AbstractImportPipeline` 固定"解析→校验→装配→持久化→报告"五步骨架，每种可导入对象（方案/维度绑定/因子赋值）以钩子实现类型差异，新增对象类型不改骨架（pricing-model §7 v1.6）；
- 并行执行模型：**校验/装配阶段用独立线程池并行**（逐行校验需查因子白名单/模板版本/维度候选集，IO 密集）；**持久化阶段仍由调用线程单事务串行执行**——MySQL 事务绑定连接不可跨线程，且"整文件要么全导要么全回滚"的原子性决定了并行写入不合法也不必要；线程池参数小而固定（core 2 / max 4 / 队列 200 / 拒绝策略 CallerRuns 自然背压），与业务线程池隔离，上报水位监控指标；
- 导出：草稿清单 / 当前生效集 / 指定方案版本时间线三种快照，只读接口走从库（§7 主从），大数据量分页流式导出，禁开长事务。

**② 方案-维度绑定管理（独立管理视图）**

- 单实例视角：列出方案实例当前/历史的维度集合全貌（IN/NOT_IN 覆盖图，未声明=全集显式化）；
- 冲突预检：编辑期即可查"与同费用哪个实例在哪一段相交"——与发布事务 S6 终态复核**同源算法前置**，把 D6 的"发布即拒"提前到"编辑即提示"，发布期仍以防不住兼做最终强制；
- 费用级视角：某费用全部并存实例的命中维度集拼接，直观暴露"默认+专属"范式的补集覆盖是否有缺口；
- 查询支撑：维度绑定表建**维度值+时间区间联合索引**（data-model v3.5 §4.2 `idx_dimval_time`，多值索引），是覆盖图/冲突预检/hit 消歧的共同数据地基；

**③ 沙盒试算（方案模拟）**

- 方案编辑后，配置人员填入一组因子样例参数 → 平台内 CalcEvaluator 解释执行 CALC 公式树 → 返回试算金额 + 公式展开过程 + 命中维度说明；支持"新旧版本对比试算"；
- **边界（D4 不变）**：试算是管理端内部接口，仅供配置验证；不进入分发契约、不承接任何在线计费订单流量；
- 语义单一来源：公式树语义规范以平台文档（pricing-model）为准，平台 evaluator 是规范的**参考实现**，下游计费执行自责实现，两侧以规范+用例集对齐。

## 5. 事务与并发设计（详见 transaction.md 修订版）

| 场景 | 手段 |
|------|------|
| 发布/回滚/下线(组粒度) | **单本地事务**（§4.1 六步协议）：事务内 fee_id 升序 FOR UPDATE 行锁 + 闭旧 CAS + 终态复核；**无 Redis 锁**（D9） |
| 草稿编辑/修改/删除 | 编辑锁（同一方案单人编辑，Redisson，D9 唯一锁）+ 行乐观锁（防锁失效后互踩），冲突返回 409 提示刷新 |
| 归档/分区/清理 job | XXL-JOB 调度中心单派发 + job 幂等（进度 CAS）；**无定时生效 job、无任务锁**（D9） |
| 状态机非法跃迁 | 领域层状态机集中校验，DB 层 `status IN (允许前置态)` 条件更新兜底 |

> MQ 投递在**事务提交后 best-effort**：不再有本地消息表兜底（决策删表），通知丢失由下游轮询生效集自愈——正确性完全不依赖 MQ。

## 6. 数据架构与容量测算（重算，详见 data-model.md）

### 6.1 量级模型（管理平台 ≠ 交易平台）

| 对象 | 估算依据 | 量级 |
|------|---------|------|
| 业务 × 场景 × 费用组/费用 | 10 业务 × 20 场景 × 若干组, 组内 3~8 费用 | 万级 |
| **pricing_scheme 版本行（最大表）** | 费用 5 万 × 年均改价 10 次 × 3 年 | ~150 万行, 窄行无大字段 |
| 维度/因子赋值/模板引用(子表) | 版本行 × 3~8 行 | ~800 万行, 仍可轻松承载 |
| 模板及因子字典 | 模板库复用 | 十万级 |
| 审计日志 | 100 运营 × 日均 50 操作 | 月分区 + 半年归档 |
| 配置读 QPS / 拉取 QPS | 内部用户 + 下游低频轮询 | < 100 QPS |

### 6.2 结论

- **不需要分库分表**（v2.1 重算后结论不变且更强）：总库量 <10GB；v2.0 的 Bundle 存储膨胀问题（~90GB）随机制删除而**消失**。**ShardingSphere 仅作预案**。
- 新成本在**装配型读**（下发需 join 子表拼版本内容）与区间扫描——由 <100 QPS + 索引点查覆盖（D8：不配缓存），可接受；
- 历史版本行/子表 `end_time < now()-3y` 迁归档库；v2.5 起分发读直查 DB（D8），读写分离、多主、本地缓存等高并发手段全部移除。

## 8. 架构决策记录（ADR，v2.0 重写）

| # | 决策 | 结论 | 理由 / 放弃的备选 |
|---|------|------|------------------|
| ADR-10 | 系统边界 | 管理平台不含计价执行/快照/交易链路（决策 D1/D3/D4 落地） | 职责单一；计算模板"定义"与"执行"分离，平台对定义的正确性负责 |
| ADR-11 | 架构风格 | 模块化单体，admin 与 delivery 预留独立部署能力 | 管理平台低 QPS；放弃 v1.0 五微服务（过度设计）；模块边界保持为未来服务边界 |
| ADR-12 | 发布一致性（v2.1 修订） | 编辑态与生效态分离：方案用 **start/end 时间区间版本行**，发布=闭旧+转正单事务原子 | 取代 v2.0 Bundle 冻结（评审删表）：定时生效零 job 依赖、时点回放即审计；代价是区间不重叠不变式需事务强制（行锁+校验） |
| ADR-13 | 双模板一致性 | 计算/展示模板在版本行内**成对锁定**（引用锁到 template_version），发布期强校验变量绑定 + content_hash 可验证 | 决策"数据一致"最关键落点不变；存储层从入 Bundle 改为挂版本行的引用+子表装配 |
| ADR-14 | 分发模式（v2.1 修订） | 拉取为主（生效集轮询 + 按时点取内容），MQ 通知 best-effort；**取消下游上报核查**（评审决策） | 时间版本化使"生效与否"由时钟定义, 无指针/缓存不一致面; 下游状态管理出圈 |
| ADR-15 | 事务方案 | 仅本地事务（沿用）；**删除本地消息表**，事件通知不做可靠投递兜底 | 管理平台写频极低, 通知丢失后果仅为下游晚一个轮询周期感知, 不构成正确性问题 |
| ADR-16 | 数据分片 | 不分库分表；历史版本行归档 + 审计月分区应对增长；ShardingSphere 为预案 | §6 重算：总库量 <10GB，行数驱动因素是费用数×改价频次 |
| ADR-17 | 并发控制（v2.5 修订） | Redis **编辑锁** + DB 乐观锁/行锁双保险；正确性以 DB 为准；**发布/job 链路无 Redis 锁**（D9） | 沿用"锁只降冲突、约束保正确"；I1/I4 最终防线在发布事务 fee 级 FOR UPDATE+终态复核（行锁按 fee_id 升序获取防死锁）；任务防重靠 XXL-JOB 单派发 |
| ADR-18 | 配置与发布单元（v2.1 新增） | 费用组为管理粒度：同页一并配置、一张审批、一个事务整组原子发布；费用带名称/编码/顺序/必填 | "一次展示一组费用"的业务语义决定天然一致性边界在组级；必填校验前移拦截缺费项 |
| ADR-19 | 不引入缓存层（v2.5 新增，D8） | 所有读接口直查 DB；删除 C1/C2/C3、预热、bypass/fail-open 全套机制 | 读压 <100 QPS 索引可扛，缓存收益覆盖不了失效链路复杂度；分发内容仍不可变（I3）——将来 QPS 上升可无损重加（预案，不预建）；放弃：v2.0 的分级缓存设计 |
| ADR-20 | Redis 职责边界（v2.5 新增，D9） | Redis 仅承担方案编辑/修改/删除排他锁；发布锁、任务锁删除；Redis 故障仅编辑入口 fail-close | 发布锁本就不是正确性参与方（DB 行锁+CAS+复核独扛），去掉后链路更短、"锁包事务"复杂度消失；任务锁与 XXL-JOB 单派发职责重叠 |
| ADR-21 | 新增功能模块落位（v2.5 新增，D10） | 批量导入导出/维度绑定管理落 pm-admin+pm-application；沙盒试算落 pm-domain（CalcEvaluator）；均不新增表 | 导入复用既有校验链产出 DRAFT，发布口径不变；试算不入分发契约，与 D4 边界兼容（配置验证 ≠ 在线计费） |

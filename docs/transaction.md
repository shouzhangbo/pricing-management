# 详细设计 · 事务与数据一致性（Transaction & Consistency）

> 上游文档：`architecture.md` v2.5（§5 事务概览、D8/D9、ADR-15/17/19/20）、`data-model.md` v3.6（§7 发布事务伪代码、§6.2 终态复核）
> 本文档定义管理平台全部写场景的事务边界、组发布六步协议、DB 行锁/乐观锁防线、不变式防线矩阵与提交后事件规范。
> **范围声明（D1~D4、D9）**：无高并发写、无交易/计价链路；**发布链路不使用 Redis 锁**；一致性关注点 = **配置数据是否一致**，不含下游应用延迟。

## 1. 设计原则（四条铁律）

| # | 原则 | 含义与推论 |
|---|------|-----------|
| P1 | **只用本地事务** | 单一 MySQL 库 → 一切写场景天然可收敛为一个 DB 事务；无 Seata/XA/最终一致补偿（ADR-15） |
| P2 | **正确性只信 DB** | 一切约束的最终防线在事务内的行锁、条件 UPDATE、唯一键与终态复核；Redis 仅剩草稿编辑锁且不在发布链路上（D9），Redis 全挂发布/分发仍正确（详见 cache-and-lock.md §3）|
| P3 | **原子边界 = 费用组** | 一次组发布 = 一个事务 = 整组生效或整组不生效；**无半发布、无组内混版**（ADR-18）|
| P4 | **不可变性优先** | 已发布的版本行及其子表行禁止 UPDATE（唯一例外：闭合 `end_time`）；改配置 = 发新版本，从根上消除"改到一半"的一致性状态 |

## 2. 事务边界规范

### 2.1 边界位置与传播

| 规则 | 说明 |
|------|------|
| 边界层 | `@Transactional` 只标注在 **pm-application 用例服务**方法上；domain/infrastructure 不开启事务 |
| 传播 | 一律 `REQUIRED`（默认）；禁止 `REQUIRES_NEW` 拆解组发布原子性 |
| 只读 | 查询用例显式 `readOnly=true`，走从库连接（如配置）|
| 超时分级 | 普通写（草稿/字典 CRUD）3s；**组发布 5s**（步骤多、含复核）；job 批处理 30s（但每批仍独立小事务，见 §8）|
| 隔离级别 | 默认 REPEATABLE READ；发布事务依赖 RR 的 next-key lock 阻塞同 fee 并发插入（§3 锁协议配合）|

### 2.2 事务内禁止事项（CI 检查项）

1. **禁止事务内远程调用**（Dubbo/HTTP/MQ）——外部副作用统一 `TransactionSynchronization.afterCommit`（§6）；
2. **禁止事务内循环大批量写**——组发布规模上限为组内费用数（≤ 百级），超出即数据异常，直接失败；
3. **禁止自调用导致注解失效**——发布编排入口 `PublishAppService.publishGroup()` 不得被同类内部方法直接调用；模板方法（AbstractTransition 状态机）中事务方法须经代理对象调用；
4. **Redis 加锁/解锁不得在事务内**——当前仅草稿编辑锁适用（§5）：事务外拿锁、提交/回滚后释放，"锁包住事务"是通用纪律；发布链路已无 Redis 锁（D9），纯靠 DB 行锁（§3.2）。

## 3. 组发布事务（核心流程）

### 3.1 六步协议（对应 data-model §7，事务内顺序）

```
前置(事务外): 组内全部方案通过提交前领域校验(因子完备/双模板配对/槽绑定B1~B5/取值合法)
              —— 快速失败, 减少进事务的无效请求

  tx.begin ────────────────────────────────────────────────────────────
  │ S1 重校验   : 事务视图内重跑关键校验(防提交前校验后数据已变)
  │ S2 锁内读   : 对涉及费用(升序) SELECT ... FOR UPDATE
  │              WHERE fee_id=? AND status='PUBLISHED' AND (end_time>NOW(3) OR end_time IS NULL)
  │              → 锁住"该费用全部未来/当前生效行"(兄弟实例), 并以 next-key lock 阻塞并发插入
  │ S3 算哈希   : 每个待转正版本 canonical 序列化 → SHA-256 → content_hash
  │ S4 闭旧     : UPDATE 同实例旧区间行 SET end_time=:newStart, row_version=row_version+1
  │              WHERE id=:curId AND row_version=:expect          -- CAS, 0 行受影响 → 抛异常回滚
  │ S5 转正     : UPDATE DRAFT 行 SET status='PUBLISHED', start_time, end_time, content_hash,
  │              row_version=row_version+1 WHERE id=? AND status='DRAFT' AND row_version=?
  │              子表(维度/因子赋值/模板引用)零写入 —— 草稿期已写好, 发布仅翻转主行状态
  │ S6 终态复核 : 事务内重建涉及费用的"发布后生效集", 两两执行:
  │              I1 同实例区间不重叠 / I4 并存实例命中维度集不相交(§6.2 交集判定)
  │              任一违规 → 抛 ConflictException → 整体回滚 + 冲突报告落 audit_log
  └────────────────────────────────────────────────────────────────────
  tx.commit → afterCommit: MQ 事件(best-effort) + 返回成功
```

**为什么 S6 放在写入后（D6 关键决策）**：同组内"默认实例 NOT_IN 缩集 + 新增广州专属"是合法变更，若逐一对比 S2 时刻的旧行会误拒；终态复核以事务视图 = 发布后终态判定，正确且回滚无中间态。S2 的行锁 + next-key lock 保证复核读到的集合在提交前不被并发改动。

### 3.2 发布并发控制：纯 DB 行锁（v2.1 起无 Redis 发布锁，D9）

```
publishGroup(groupId):
  transactionTemplate.execute(status -> doPublish())   // 直接进入事务, S1~S6
  // 并发控制全部在事务内: S2 对涉及费用按 fee_id 升序逐个 FOR UPDATE
  //   → 同一费用(含同组不同人触发)的并发发布被行锁天然串行化
  //   → 升序获取 = 全局锁序一致, 结构性防死锁
  //   → next-key lock 同时阻塞同 fee 并发插入
```

- **同组/同费并发发布**：后到事务等行锁；`innodb_lock_wait_timeout` 配为 3s（< 事务 timeout 5s），超时即整组回滚，返回明确提示"存在进行中的发布，请稍后重试"——发布是人工低频操作，排队概率极低；
- **为什么去掉原 Redis 组/费用发布锁**（ADR-20）：它从来不是正确性参与方（P2），只降冲突；写频极低下冲突窗口可忽略，去掉后"锁包事务"的边界复杂度消失；
- Redis 不可用：对发布链路**零影响**（不在发布路径上）。

### 3.3 失败语义矩阵

| 失败点 | 结果 | 用户可见行为 |
|--------|------|-------------|
| 提交前校验失败 | 不进事务 | 表单级错误定位到具体费用/因子 |
| 行锁等待超时（并发发布撞车）| 整组回滚 | "存在进行中的发布，请稍后重试" |
| S1~S6 任一步异常 | **整组回滚**，全部费用停留旧版本 | 错误码 + 冲突报告（I1/I4 违规：哪个城市/网格与哪个实例碰撞）|
| commit 后 afterCommit 失败 | 发布已成功，仅通知缺失 | 无感知；下游 ≤60s 后轮询自愈（§6）|

## 4. 不变式防线矩阵（谁保证什么）

| 约束 | DB 声明式 | 事务内强制 | 领域前置校验 |
|------|----------|-----------|-------------|
| 实例时间线唯一 **I1** | `uk_root_scheme_start(root_scheme_id,start_time)` 防同刻双开 | S6 区间重叠复核（重叠无法用唯一键表达）| 提交前预检（UX 级）|
| 闭旧转正原子 **I2** | — | S4+S5 同一事务 + CAS | — |
| 已发布不可改 **I3** | 权限/SQL 规约 + S5 仅动主行状态列 | 发布路径外无 UPDATE PUBLISHED 行的用例 | 编辑入口只开放 DRAFT |
| 维度互斥 **I4** | — | S6 终态复核（§6.2 笛卡尔积交集判定）| 提交前预检 |
| 双模板成对 | `uk_scheme_type(scheme_id,template_type)` | — | B1~B5 绑定校验矩阵 |
| 组内费用顺序唯一 | `uk_group_seq(group_id,seq_no)` | — | 页面配置校验 |
| 状态机合法跃迁 | 条件 UPDATE `WHERE status IN(前置态)` | CAS row_version | AbstractTransition 集中校验 |
| 审批后置动作唯一 | `uk(biz_type,biz_id,action)` 于 approval_flow | 同事务 S 步 | — |

> 口诀：**能用唯一键的进 DDL，区间/集合类进事务复核，体验类前置预检**。三层互为冗余，任何单层失效不破坏正确性。

## 5. 草稿编辑并发（轻量场景）

| 层 | 手段 | 语义 |
|----|------|------|
| 第一层 | 编辑锁 `pm:lock:edit:{schemeId}`（TTL 90s + 看门狗续期，owner=userId）| 单人编辑体验，UI 显示"XX 正在编辑" |
| 第二层 | 行 `row_version` CAS | 编辑锁失效后互踩的最终防线，0 行受影响返回 **409 + 数据版本冲突**，前端引导刷新合并 |

- 草稿期子表（维度/因子赋值/模板引用）允许自由改：采用**全删重建**（DELETE + 批量 INSERT，同一事务），避免逐行 diff 的复杂度——发布后不可变使草稿期是唯一可变窗口；
- DRAFT 行删除 = 逻辑删（status→CANCELLED），保留审计链。

## 6. 提交后事件（afterCommit，best-effort）

| 事件 | 监听动作 | 丢失后果 |
|------|---------|---------|
| `SchemePublishedEvent` | 投 MQ `PRICING_PUBLISH_NOTIFY`（异步、失败仅日志+告警计数）| 下游少收一次"提前感知"通知 |

- v2.1 起监听动作**不含清缓存**（D8 无缓存层）；

- **无本地消息表、无重试补偿**（v1.0 机制已随 D2/ADR-15 删除）：分发正确性完全由拉取模型保证——下游轮询 `effectiveSet`，以 `(contentHash, startTime)` 感知变化；通知只是加速，**丢失不构成任何不一致**；
- 实现：Spring 事件 + `@TransactionalEventListener(phase=AFTER_COMMIT)`；监听器内禁止再开写事务（当前无此需求，CI 检查）。

## 7. 定时生效与时间语义（零 job 设计）

- 区间统一 **[start_time, end_time)**（左闭右开），切换瞬间无重叠、无空洞；
- 定时发布 = S4/S5 写入未来 `:newStart`：旧行 end 提前闭合 = 新版本 start，**时间一到时钟自身完成切换**，无任何生效 job；
- 复核 S6 按"区间相交"而非"当前时刻"判定：未来区间之间同样必须满足 I1/I4，防止"今天合法、下周二两实例同时生效"的潜伏冲突；
- 单时区（东八区）DATETIME(3)（D7）：所有比较以 DB `NOW(3)` 为唯一时钟源，应用实例不各用自己的本地时间。

## 8. Job 事务规范（归档/分区维护）

| 规则 | 说明 |
|------|------|
| 防重 | XXL-JOB 调度中心单派发 + 路由策略（v2.1 起无 Redis 任务锁，D9）；job 自身幂等作第二道防线 |
| 小事务 | 每批（≤500 版本行）一个独立事务，禁止整表一个大事务；进度表 CAS 推进，天然幂等可断点续跑 |
| 归档对象 | `end_time < now()-3y` 的闭合版本行及子表 → 归档库同构表；audit_log 月分区滚动 DROP |
| 边界 | 归档只碰已闭合行（I3 保证内容不变），与发布事务无锁冲突（发布 S2 只锁开区间/未来行）|

## 9. 一致性验证清单（上线前必测）

1. **组原子性**：构造 S6 复核冲突（两实例争同一城市），断言整组回滚、全部费用旧区间仍开放、audit_log 有冲突记录；
2. **并发发布**：两会话同时对同一 fee 发不同新实例（维度重叠），断言仅一方成功（FOR UPDATE 行锁串行化 + 超时回滚）；
3. **同组原子变更**：默认实例 NOT_IN 缩集 + 新增专属实例同批发布，断言 S6 通过、生效瞬间维度全覆盖无空洞；
4. **Redis 故障隔离**：关闭 Redis 重跑 1~3，断言发布结果完全不变（发布链路不依赖 Redis，D9）；同时断言编辑入口 fail-close 拒绝、分发/查询正常（cache-and-lock.md §3）；
5. **定时切换**：newStart=+2min 发布，断言当刻旧行已闭、到点后 `effectiveSet` 返回新集，全程无 job；
6. **CAS 冲突**：模拟编辑锁过期后双用户先后提交 DRAFT 修改，断言后者 409。
